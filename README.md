# 문서를 제대로 찾는 챗봇을 만들어 보고 싶었습니다

Operational RAG — Papybot Green

`Python` · `FastAPI` · `BM25` · `TF-IDF` · `RRF` · `pytest`

처음 이 프로젝트를 시작할 때 떠올린 상황은 간단했습니다. 회사에서 VPN 오류가 났을 때 해결 방법이 문서 어딘가에 적혀 있는데, 그걸 찾으려고 여러 파일을 뒤지는 상황입니다. 이런 문서를 챗봇으로 물어볼 수 있다면 편하겠다고 생각했습니다.

그런데 만들면서 생각이 조금 바뀌었습니다. 답변을 자연스럽게 만드는 것도 중요하지만, 그보다 먼저 맞는 문서를 찾아야 했습니다. 검색 결과부터 틀리면 아무리 그럴듯하게 답해도 도움이 되지 않기 때문입니다. 그래서 이 프로젝트에서는 답변 생성 모델 자체보다는 문서를 준비하고, 질문과 관련된 내용을 검색하고, 근거를 보여주는 과정에 더 집중했습니다.

현재는 로컬에서 실행하는 학습용 프로토타입입니다. 실제 회사 문서를 연결한 운영 서비스는 아닙니다.

## 직접 실행한 챗봇 화면

![로컬에서 실행한 Papybot Green 챗봇](./papybot%20green.png)

위 화면은 로컬 환경에서 챗봇을 실행한 모습입니다. 예를 들어 `VPN 오류 720 해결 방법`처럼 기술 문서에 있는 내용을 질문하고 검색된 결과를 확인할 수 있도록 만들었습니다. 화면이 동작한다는 것과 답변이 언제나 정확하다는 것은 다른 문제라서, 검색 성능은 아래와 같이 따로 확인했습니다.

## 어떤 방식으로 만들었나

전체 흐름은 다음과 같습니다.

```text
사용자 질문
    ↓
FastAPI /chat
    ↓
QAService → Agent
    ↓
Retriever
  ├─ BM25
  └─ 문자 n-gram TF-IDF
    ↓
RRF로 검색 순위 결합
    ↓
관련 문서와 출처 확인
    ↓
LLM 연결 시 답변 생성 / 연결 실패 시 근거 문서 발췌
    ↓
웹 화면 또는 API로 결과 반환
```

FastAPI는 질문을 받고 결과를 돌려주는 역할을 하고, 검색은 `rag/retriever_v2.py`, 답변 처리는 `rag/generator.py`로 나눴습니다. 한 파일에 모두 넣을 수도 있었지만 검색 결과가 이상한 건지, 답변 생성 과정에서 문제가 생긴 건지 구분하기 어려울 것 같았습니다. 나중에 검색 방법을 바꿔 보기도 쉽게 하고 싶었습니다.

## 만들면서 고민했던 부분

### 1. 문서가 있다고 해서 모두 검색해도 될까?

처음에는 폴더에 있는 문서를 전부 읽어서 검색하면 된다고 생각하기 쉽습니다. 하지만 오래되었거나 검증되지 않은 사용법이 검색되면 오히려 잘못된 안내를 할 수 있습니다. 특히 오류 해결 방법처럼 사용자가 그대로 따라 할 만한 내용이라면 더 조심해야 한다고 생각했습니다.

그래서 Markdown 문서의 앞부분에 상태 정보를 두고, `status: verified`와 `publishable: true`를 모두 만족하는 문서만 검색 대상으로 넣었습니다. 조건에 맞지 않는 문서는 제외하도록 했습니다.

물론 이 설정만으로 문서의 내용이 정말 맞다고 보장되는 건 아닙니다. 누군가 확인했다는 상태를 표시하고 검색 대상을 제한하는 첫 단계에 가깝습니다. 사용자별 문서 접근 권한까지 처리하는 기능도 아직 없습니다.

### 2. 질문에 맞는 문서를 어떻게 찾아야 할까?

가장 신경 쓴 부분입니다. `VPN 오류 720`처럼 오류 번호가 정확히 들어가는 질문은 그 번호 자체를 놓치면 안 됩니다. 그래서 단어의 중요도를 반영하는 BM25를 먼저 사용했습니다.

그런데 문서와 질문의 표현이 조금 다를 수도 있습니다. 이를 보완하려고 문자 단위의 n-gram을 사용하는 TF-IDF 검색을 함께 넣었습니다. 두 검색 방법은 점수 계산 방식이 다르기 때문에 점수를 그대로 더하기보다 RRF(Reciprocal Rank Fusion)로 각 검색 결과의 순위를 합쳤습니다.

여기서 한 가지는 분명히 구분해야 합니다. 지금 기본 설정의 TF-IDF는 문자의 겹침을 이용한 검색이지, 문장의 뜻을 이해하는 임베딩 검색은 아닙니다. 실제 의미 검색을 비교해 보고 싶어서 `sentence-transformers`를 사용하는 선택 경로도 따로 두었습니다. 다만 임베딩을 사용했다고 무조건 더 좋은 결과가 나온다고 생각하지는 않습니다. 같은 질문으로 비교해 봐야 알 수 있는 부분입니다.

### 3. LLM이 연결되지 않으면 챗봇도 멈춰야 할까?

답변 생성 API가 정상적으로 연결되지 않는 상황도 고려해야 했습니다. 검색은 잘 됐는데 외부 API 호출 문제 때문에 아무 결과도 보여주지 못한다면 사용하기 불편할 것 같았습니다.

그래서 LLM API 키를 설정하지 않았거나 생성 요청에 실패하면, 답변을 억지로 만들어 내는 대신 검색한 문서의 발췌 내용과 출처를 보여주도록 했습니다. 이때는 생성형 답변이 아니라 검색 결과를 보여주는 모드입니다.

이 부분을 만들면서 챗봇의 품질이 단순히 LLM 모델에만 달린 게 아니라는 점을 더 생각하게 됐습니다. 검색이 잘되는지, 실패했을 때 어떻게 처리하는지, 사용자가 원문을 확인할 수 있는지도 중요했습니다.

### 4. 결과가 나오면 제대로 작동한다고 볼 수 있을까?

브라우저에서 질문을 입력하고 답이 나온다고 해서 검색 품질까지 확인된 건 아닙니다. 엉뚱한 문서를 찾아도 답변 형식만 그럴듯할 수 있기 때문입니다.

그래서 `data/golden.json`에 질문과 관련 문서를 정리하고 Hit@k, Recall@k, MRR@k를 계산하는 평가 코드를 넣었습니다. LLM이 어떤 문장으로 답변하는지와 관계없이, 우선 검색 단계에서 필요한 문서를 상위 결과에 가져오는지를 확인하기 위해서입니다. API와 주요 기능은 `pytest` 테스트로 점검할 수 있게 했고, `/metrics`에서는 요청과 처리 시간 등을 확인할 수 있게 했습니다.

현재 평가 질문은 소수의 예제 수준입니다. 여기서 점수가 높더라도 실제 회사의 수많은 문서와 다양한 질문에서 잘 작동한다는 뜻은 아닙니다. 다음에는 질문 표현을 바꾼 경우, 비슷한 오류 코드가 함께 있는 경우, 정답 문서가 없는 경우를 더 넣어서 비교해 보고 싶습니다.

## 로컬에서 실행하기

macOS와 Python 3.11–3.13 환경을 기준으로 정리했습니다. 프로젝트 폴더 안에서 실행합니다.

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
cp .env.example .env
python -m uvicorn main:app --reload --port 8000
```

서버를 실행하면 아래 주소에서 확인할 수 있습니다.

- 챗봇 화면: http://127.0.0.1:8000/
- API 문서: http://127.0.0.1:8000/docs
- 상태 확인: http://127.0.0.1:8000/health
- 기본 메트릭: http://127.0.0.1:8000/metrics

`LLM_API_KEY`는 비워 두어도 됩니다. 이 경우 LLM 답변 생성 대신 검색 문서 발췌를 보여줍니다. 실제 생성형 답변을 사용하려면 `.env`에 별도의 API 키를 설정해야 합니다.

API로 직접 질문해 볼 수도 있습니다.

```bash
curl -s http://127.0.0.1:8000/chat \
  -H 'Content-Type: application/json' \
  -d '{"message":"VPN 오류 720 해결 방법","top_k":3}'
```

테스트와 검색 평가:

```bash
python -m pytest -q
python scripts/run_eval.py --retrieval-only --k 1
python scripts/run_eval.py --retrieval-only --k 3
```

## 문서 추가와 검색 방식 변경

새 문서를 넣을 때는 `data/docs/`에 Markdown 파일을 만들고 다음과 같이 상태 정보를 적습니다.

```yaml
---
title: VPN 연결 문제 해결
status: verified
publishable: true
---
```

이후 본문에 검증한 해결 방법을 작성하면 됩니다. 현재는 문서를 수정한 뒤 서버를 다시 시작해야 검색에 반영됩니다.

임베딩 기반 검색을 시험하려면 서버를 중지하고 아래 패키지를 추가로 설치합니다.

```bash
python -m pip install -r requirements-semantic.txt
```

`.env`에 `RAG_EMBEDDING_BACKEND=sentence_transformers`를 설정한 뒤 다시 실행합니다. 최초 실행에는 모델 다운로드가 필요할 수 있습니다.

## 돌아보면서

처음에는 RAG를 만든다고 하면 LLM을 연결하는 일이 가장 핵심이라고 생각했습니다. 하지만 직접 구성해 보니 좋은 답변을 만들기 전에 해결해야 할 일이 많았습니다. 어떤 문서를 검색 대상으로 삼을지, 질문과 문서의 표현이 다를 때 어떻게 찾을지, 검색이 제대로 됐는지 어떻게 확인할지가 더 어렵고 중요하게 느껴졌습니다.

아직 실제 운영 환경에서 쓸 수 있는 수준은 아닙니다. 문서별 접근 권한도 없고, 평가에 사용한 질문도 적습니다. 다음에 이 프로젝트를 더 발전시킨다면 문서 수와 평가 질문을 먼저 늘리고, BM25·TF-IDF·임베딩 검색을 같은 조건에서 비교해 보고 싶습니다. 검색 결과가 틀리는 사례를 모아 보는 것이 새로운 기능을 추가하는 것보다 먼저일 수도 있겠다는 생각이 듭니다.

이 프로젝트는 `learning-guide.template(1).md`의 서비스 구조를 참고해 학습 목적으로 직접 재구성했습니다. 가이드에 등장하는 운영 서비스의 전체 기능을 복제한 것은 아닙니다.
